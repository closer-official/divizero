## 7-1【重大】48hチェックがFirestore書き込みの無限ループになる — `src/App.tsx`

### 現象
フェーズ6-3の定期チェック化で、効果が次の構造になっている:

```tsx
useEffect(() => {
  if (loading) return
  runPipelineChecks()                                  // 即時実行
  const timer = setInterval(runPipelineChecks, 60 * 60 * 1000)
  return () => clearInterval(timer)
}, [loading, data.pipeline])                           // ← pipeline変化のたびに再実行
```

一方 `runPipelineChecks()` 内の48hマーキングは:

```tsx
if (!p.last_reaction || p.last_reaction_at !== latestTouch.date) {
  updated = { ...updated, last_reaction: 'none' as const, last_reaction_at: now.toISOString() }
}
```

書き込む値が `now.toISOString()` なのに比較相手が `latestTouch.date` のため、**条件は永遠に真**。
→ 48h超の `awaiting_reaction` タッチを持つ案件が1件でもあると、
「saveData → `data.pipeline` 変化 → effect再実行 → 即 `runPipelineChecks()` → また saveData → …」の**無限書き込みループ**になる。

### 修正内容（2点セット。両方必須）

**(1) effectの依存から `data.pipeline` を外し、即時実行はマウント時1回にする**

- effect の依存配列を `[loading]` のみにする
- `runPipelineChecks()` が古いデータを見ないよう、関数内の `data.pipeline` / `data` 参照をすべて **`dataRef.current`**（App.tsx に既存の ref）経由に書き換える。これで60分interval発火時も最新データを読める
- トースト重複防止の `notifiedRecontactIdsRef` は現状のまま維持

**(2) 48hマーキングのdedup条件を直す**

`last_reaction_at` の意味（＝last_reactionを更新した時刻。Tab2の他箇所はすべて `new Date().toISOString()` を保存）は**変えない**。比較側を「このタッチに対して既にnoneマーク済みか」を正しく判定する形にする:

```tsx
const alreadyMarked =
  p.last_reaction === 'none' &&
  !!p.last_reaction_at &&
  p.last_reaction_at >= latestTouch.date   // ISO文字列の辞書順比較でOK（last_reaction_atはフルISO、touch.dateはその接頭辞形式）
if (!alreadyMarked) {
  updated = { ...updated, last_reaction: 'none' as const, last_reaction_at: now.toISOString() }
}
```

- 新しいタッチが増えて再び48h経過した場合は `latestTouch.date > last_reaction_at` になるので再マークされる（正しい挙動）
- ユーザーが実反応（heart等）を記録済みの場合は `last_reaction !== 'none'` なので上書きされる（従来と同じ）

**(3) `needsUpdate` の判定も (2) と同じ条件にそろえる**

現在の `needsUpdate` は「48h超のawaiting_reactionがあるか」だけを見ており、マーク済みでも毎回 `saveData` が走る。48h側の判定を `!alreadyMarked` を含む形にし、**実際に書き換わる案件がある時だけ** `saveData` を呼ぶ。判定ロジックが2箇所に分かれて食い違わないよう、`shouldMarkNoReaction(p, latestTouch)` のようなローカル関数に切り出して両方から使うこと。

### 受け入れ基準
1. 48h超の `awaiting_reaction` タッチを持つ案件がある状態でアプリを開き、DevToolsのNetworkタブ（またはFirestoreコンソール）で**書き込みが1回で止まる**こと（従来はループする）
2. リロードしても再度の書き込みが発生しない（マーク済みのため）
3. `recontact_date` 到来案件の waiting→active 遷移とトースト通知は従来どおり動く
4. `npm run build` 成功

## 7-2【バグ】`force` フラグがbackgroundで捨てられ、上書き確認が無限ループ — `service_worker.js`

### 現象
`chrome.runtime.onMessage` の `s1_touch_start` ハンドラが:

```js
const { handle, tweetUrl, tweetText } = message
handleS1TouchStart({ handle, tweetUrl, tweetText, xTabId }, sendResponse)
```

と `message.force` を取り出しておらず、`handleS1TouchStart` の `if (!force)` ガードが常に有効。
→ scannerの confirm で「OK」を押して `force: true` で再送しても再び `CONTEXT_EXISTS` が返り、**確認ダイアログが無限に出続ける**。

### 修正内容

```js
const { handle, tweetUrl, tweetText, force } = message
handleS1TouchStart({ handle, tweetUrl, tweetText, force, xTabId }, sendResponse)
```

### 受け入れ基準
1. S1接触の取込前に別ツイートのS1接触を押す → confirm → OK → **1回で**新しい対象に切り替わり、Geminiに新プロンプトが挿入される
2. confirm → キャンセル → ボタンが「💬 S1接触」に戻り、前のコンテキストが保持されている

## 7-3【バグ】OS②タッチの自動取込が meta なしで送られ、出力が黙って消える — `gemini_filler.js` / `service_worker.js`

### 現象
- `startS1AutoCaptureWatch()` のtickがタッチモード時 `void captureTouchOutput(current, true)` と呼び、**第4引数 `meta` がnullのまま**。
- background の `handleTouchOutputCaptured(raw, meta, ...)` は `meta.pipelineItemId` が無いと**無言でreturn**。
- 一方UIは「✓ 自動取込しました。Webアプリへ戻ります…」と表示してパネルを閉じるため、**成功に見えて出力が失われる**（手動【取込】はmetaを渡しており正常）。

### 修正内容

**(1) gemini_filler.js — metaをモジュールスコープで保持して自動取込に渡す**

```js
let touchGeminiPanelMeta = null   // 変数宣言部に追加
```

- `showTouchCapturePanel(meta, promptText)` の冒頭で `touchGeminiPanelMeta = meta || null`
- `closeTouchCapturePanel()` で `touchGeminiPanelMeta = null`
- tick内のタッチモード分岐を `void captureTouchOutput(current, true, undefined, touchGeminiPanelMeta)` に変更
  （`sourceLabel` のデフォルトを崩さないよう `undefined` を明示的に渡すか、`captureTouchOutput` 内で `meta = meta ?? touchGeminiPanelMeta` とフォールバックする。どちらでもよいが一方に統一）

**(2) service_worker.js — 無言破棄をやめてGemini側にエラーを返す（防御層）**

`handleTouchOutputCaptured` の先頭:

```js
if (!pipelineItemId || typeof raw !== 'string') {
  console.warn('[Touch Output] captured without pipelineItemId, dropping')
  if (geminiTabId) {
    try { chrome.tabs.sendMessage(geminiTabId, { type: 'touch_output_result', result: { ok: false, code: 'NO_META' } }) } catch (_) {}
  }
  return
}
```

**(3) gemini_filler.js — `touch_output_result` の失敗を表示する**

既存の `chrome.runtime.onMessage` リスナー（`os0_import_result` を処理している箇所）に追加:

```js
if (message.type === 'touch_output_result' && message.result?.ok === false) {
  showError('取込コンテキストが失われました。Webアプリの「コピーしてGeminiを開く」からやり直してください。')
  return
}
```

### 受け入れ基準
1. Tab2「タッチ追加」→「コピーしてGeminiを開く」→ Geminiで送信 → **自動取込ON**のまま応答完了を待つ → Webアプリにフォーカスが戻り、AI出力欄と解析結果が自動で埋まる（フェーズ6-1の受け入れ基準が自動モードでも通る）
2. 手動【取込】も従来どおり動く（回帰確認）

## 7-4【高リスク・要実機確認】URL変化で送信検知バーが破棄され、Touch記録が失われる競合 — `s1_touch_scanner.js`

### 現象（机上推定。まず実機で再現確認すること）
`s1HandleUrlChange()` に `s1RemovePendingBar()` が入っている。Xは返信モーダルの開閉で `/compose/post` ⇄ 元URL のpushStateを発火するため、次の競合が起こりうる:

1. ユーザーがXの送信ボタンをクリック → 検知リスナーが `setTimeout(800ms)` で記録を予約
2. モーダルが閉じてURLが元に戻る → `s1HandleUrlChange` → `s1RemovePendingBar()` がバーとリスナーを破棄
3. 800ms後の記録処理が `if (!s1PendingBar) return` ガードで**スキップされ、Touchが記録されない**

### 実機確認手順
S1接触フローを最後まで実行し「Aで返信」→ Xの送信ボタンで実送信 → Tab2の該当案件にTouchが記録されるか確認する。**記録される場合でも以下の修正は予防として実施する**（タイミング依存の競合のため、一度成功しても安全とは言えない）。

### 修正内容

**(1) 記録可否をバーDOMの生存に依存させない**

```js
let s1PendingActive = false   // 変数宣言部に追加
```

- `s1ShowPendingBar()` の冒頭（`s1RemovePendingBar()` の後）で `s1PendingActive = true`
- `finish(recorded)` のガードを `if (!s1PendingBar) return` から `if (!s1PendingActive) return` に変え、直後に `s1PendingActive = false` を立ててから `s1RemovePendingBar()` を呼ぶ
- 送信検知リスナー内の `if (s1PendingBar && !s1PendingRecorded)` も `s1PendingActive` ベースに変更
- 10分タイムアウトのハンドラも同様に `s1PendingActive` を確認・クリアする形にそろえる

**(2) URL変化ではバーを消さない**

`s1HandleUrlChange()` から `s1RemovePendingBar()` の呼び出しを削除する。バーの寿命は「記録/スキップ/10分タイムアウト」の3経路だけで管理する（返信モーダルの開閉による一時的なURL変化で作業状態を失わないため）。

### 受け入れ基準
1. S1接触 → A/B選択 →「Aで返信」→ Xの送信ボタンで実送信 → 約1秒後に「送信を検知しました」トースト → Tab2にTouchが記録される（**モーダル閉鎖のURL変化があっても記録される**）
2. 送信せずにモーダルを閉じてタイムライン閲覧を続けてもバーは残り、「記録しない」で消える
3. 10分放置で自動スキップ（従来どおり）
