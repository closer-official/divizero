## 6-1（B3）: Tab2「コピーしてGeminiを開く」の出力取込を自動化する

### 現状
Tab2 の CaseCard（タッチ追加フォーム）の `handleCopyAndOpenGemini()` は `setGeminiPrompt(prompt)` でGeminiへの自動挿入までは行うが、**出力はユーザーが手動でコピーしてTab2の「AI出力」textareaに貼り付け、解析ボタンを押す**必要がある。フェーズ3で作った取込機構をここにもつなげる。

### 設計
1. `set_gemini_prompt` メッセージ（`ReceiveService.setGeminiPrompt` → `service_worker.js` の `onMessageExternal`）に meta を追加:
   ```ts
   // ReceiveService.setGeminiPrompt(text, meta?: { pipelineItemId: string; kind: 'touch' })
   { type: 'set_gemini_prompt', text, meta }
   ```
   `service_worker.js` は `os2_gemini_prompt: { text, meta, setAt }` として保存する（後方互換: metaなしも許容）。
2. `gemini_filler.js` の `tryFill()`（OS②プロンプト挿入）を変更: `entry.meta?.pipelineItemId` がある場合、挿入後に**取込パネルを表示**する（S1パネルを流用した `showTouchCapturePanel(entry.meta)`）。
   - マーカーはタッチ出力の `'TOUCH_START'` / 自動取込判定は `'TOUCH_END'`（フェーズ3の機構をそのまま再利用。自動取込トグルも共通）
   - 従来どおり `os2_gemini_prompt` キーは挿入時に削除するが、metaは取込完了まで必要なので、パネル表示用にローカル変数で保持する
3. 取込結果は background へ `{ type: 'touch_output_captured', raw, meta }` で送り、backgroundが**既存キュー（`os_ext_queue`）に enqueue** する:
   ```js
   { id, type: 'gemini_touch_output', status: 'pending', payload: { raw, pipelineItemId: meta.pipelineItemId }, enqueuedAt }
   ```
   enqueue後 `openOrFocusWebapp()` でWebアプリへフォーカスを戻す。
4. Webアプリ側: `src/services/receive/types.ts` に `gemini_touch_output` 型を追加。`useReceive` に `touchOutputPending` フィルタを追加。
5. `Tab2.tsx` の CaseCard に効果を追加: タッチ追加フォームが開いていて（`addingTouch`）、`touchOutputPending` に `payload.pipelineItemId === item.id` の項目があれば:
   - `setAiOutput(payload.raw)` して既存の解析処理（`handleAutoFill()` と同じロジック）を自動実行
   - `markCompleted(項目id)`、`toast.show('Geminiの出力を自動取込しました')`
   - 既存の `os2Applied` と同様の一回ガード（`touchOutputApplied` state）を付ける

### 受け入れ基準
- Tab2でタッチ追加 → 「コピーしてGeminiを開く」→ Geminiで送信 → 応答完了 → **Webアプリに自動でフォーカスが戻り、AI出力欄と解析結果（投稿本文・A/B案）が自動で埋まっている**

## 6-2（B4）: 「OS②選択」後の案件到達導線を短縮する

### 現状
拡張の「OS②選択」→ enqueue → Webアプリが開くが、ユーザーは該当案件を**自分で探して開き**、「タッチ追加」を押して初めてURL自動入力が発動する（CaseCardの `os2Pending` effect が `addingTouch=true` を条件にしているため）。

### 変更 — `Tab2.tsx`
1. `useReceive()` の呼び出しを **CaseCard から Tab2 のトップレベルコンポーネントへ移動**する（ポーリングの一本化も兼ねる）。CaseCard には必要な値（`os2Pending` / `touchOutputPending` / `markCompleted` / `setGeminiPrompt` / `connected`）をpropsで渡す。
2. Tab2トップレベルに効果を追加: `os2Pending` に、表示中パイプラインとハンドル一致する項目が現れたら:
   - 該当 `PipelineItem` のドロワーを自動で開く（既存の `setDrawerItemId` を使う）
   - CaseCard に `autoStartTouch: true` 相当のpropを渡し、CaseCard側でマウント時に `startAddTouch()` を自動実行 → 既存の `os2Pending` 自動入力effectがそのまま発火してURL・投稿本文が埋まる
   - 自動オープンは1キュー項目につき1回だけ（処理済みキューidを `useRef<Set<string>>` で管理）
3. ハンドル照合は既存effectと同じ `normalizeHandle` 比較を使う。一致する案件がない場合は何もしない（従来どおり）。

### 受け入れ基準
- x.comで「OS②選択」→ Webアプリにフォーカスが移ると、**該当案件のドロワーとタッチ追加フォームが自動で開き、ツイートURL・投稿本文が入力済み**になっている
- Tab2を表示していない場合でも、Tab2を開いた時点で同様に自動オープンする（useReceiveがTab2マウント時にポーリング開始するため）

## 6-3（B5）: 48h無反応・再接触日チェックの定期実行

### 現状
`App.tsx` の起動時チェック（`recontactCheckDone` ref のuseEffect）は**アプリロード時に1回だけ**実行。タブを開きっぱなしの運用では翌日になってもリロードするまで発火しない。

### 変更 — `App.tsx`
1. 既存の起動時チェックeffectの中身を `runPipelineChecks()` 関数に抽出する（ロジックは一切変えない。`dataRef.current` を読むようにして依存を切る）
2. マウント時に1回実行（従来どおり）＋ `setInterval` で**60分ごと**に再実行する。effectのクリーンアップで `clearInterval`
3. トースト通知の重複防止: 通知済みの案件IDを `useRef<Set<string>>` に保持し、同一セッションで同じ案件の再接触通知を繰り返さない
4. `recontactCheckDone` ref は不要になるので削除してよい

### 受け入れ基準
- `recontact_date` を現在時刻の直後に設定した案件を用意し、リロードせず60分後（検証時はintervalを一時的に1分に縮めてよい。**コミット前に60分へ戻す**）にstateが `active` に変わりトーストが出る
- 同じ案件の通知が繰り返し出ない

## 6-4（C）: 小さな無駄の掃除

1. **OS⓪プロンプトキャッシュTTL短縮**: `service_worker.js`（フェーズ4で移設済み）の `CACHE_TTL_MS` を `60 * 60 * 1000`（1時間）に変更。`popup/popup.html` / `popup.js` に「プロンプトキャッシュをクリア」ボタンを追加（`chrome.storage.local.remove('os0_prompt_cache')` → 表示更新）
2. **キューの自動掃除**: `service_worker.js` の enqueue 処理時に、`status !== 'pending'` かつ `enqueuedAt` が7日超の項目をキューから除去してから保存する
3. **デッドコード削除**:
   - `src/services/receive/types.ts` の `os0_candidates` 型と、`useReceive.ts` の `os0Pending` / `os0History`（enqueueする側がどこにも存在しない）
   - `useReceive.ts` の `markDismissed` / `restore` / `clearHistory` — **削除前にgrepで参照ゼロを確認**。6-1/6-2の実装で使うことになった場合は残す
   - 削除の際、`ExtQueueItem` 型のユニオンから漏れた参照がないか `npm run build` で確認
4. **デバッグログ削減**: `ReceiveService.ts` / `useReceive.ts` の `console.log`（`[OS Ext RS]` / `[OS Ext Hook]` プレフィックス）を削除。`console.warn` のエラー系は残す
