## 8-1: ボタンが初回表示時に出ない問題の修正（DOMリサイクル対策）

### 原因
Xのタイムラインは仮想化されており、`article` 要素を**リサイクル**する。現在は `article.dataset.os2Injected` / `data-s1-injected` のフラグだけで注入済み判定しているため、**Xが中身を再レンダリングしてボタンDOMを消してもフラグが残り、そのarticleには二度と注入されない**。「Geminiから戻ると表示される」のはタブ復帰時にXがノードを作り直すため。

### 変更1 — `profile_panel.js` の `os2InjectButtons()`

ループ先頭の判定を「フラグ＋ボタン実在」に変える:

```js
for (const article of articles) {
  const hasBtn = !!article.querySelector('.os2-select-btn')
  if (article.dataset.os2Injected && hasBtn) continue   // 正常に注入済み
  if (article.dataset.os2Injected && !hasBtn) {
    delete article.dataset.os2Injected                   // リサイクルでボタンが消えた → 再注入へ
  }
  if (hasBtn) { article.dataset.os2Injected = '1'; continue }  // フラグ欠落だがボタンあり（保険）
  if (os2IsRetweet(article)) continue
  ...以下既存のまま
}
```

### 変更2 — `s1_touch_scanner.js` の `s1InjectButtons()`

同じパターンを適用（ボタンセレクタは `.s1-touch-btn`）。注意点:
- パイプラインハンドルのフィルタ（`s1PipelineHandles` 照合）は**実在チェックの後・フラグ設定の前**という現在の順序を維持する（フィルタで弾いた article にフラグを立てない、はフェーズ2のまま）
- S1ボタンは既存の `.os2-btn-wrapper` に相乗りする実装のため、リサイクルで wrapper ごと消えた場合・wrapper だけ残った場合の両方で正しく再注入されることを確認する

### 変更3 — 両ファイルに定期再スキャンとタブ復帰時スキャンを追加

各ファイルの末尾（既存の `〜ScheduleScan()` 初回呼び出しの近く）に追加:

```js
// MutationObserverの取りこぼし対策（3秒間隔のセーフティネット）
setInterval(os2ScheduleScan, 3000)   // s1側は s1ScheduleScan

// タブ復帰時（Gemini等から戻った時）に即スキャン
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'visible') os2ScheduleScan()   // s1側は s1ScheduleScan
})
```

※どちらもデバウンス済み関数を呼ぶだけなので負荷は無視できる。`twitter_scraper.js`（OS⓪ボタン）は毎スキャンで全カード再収集する設計なので変更不要。

## 8-2: 取得済みの投稿原文をタッチプロンプトへ自動挿入する

### 原因
テンプレート `public/prompts/OS_継続接触_タッチ生成_latest.md` は末尾「【相手の新規投稿スクリーンショット】：（以下に添付）」のスクショ前提設計。拡張は投稿本文を取得済み（S1フローの `tweetText`、OS②フローの `postText`）なのにプロンプトへ渡す経路がなく、ユーザーがスクショ添付か手動貼り付けを強いられている。
**プロンプトファイル自体は変更しない**（禁止事項）。アプリ側で末尾にセクションを付加する。

### 変更1 — `src/utils/touchPrompt.ts`

型と関数シグネチャを拡張（**後方互換必須**。既存呼び出しは全てそのまま動くこと）:

```ts
}
```

`buildInboundTouchPrompt` は独自に自分の投稿情報を組み込む別系統なので**変更しない**（内部の `buildTouchPrompt` 呼び出しも targetPost なしのまま）。

### 変更2 — `src/services/extensionBridge.ts` の `GET_TOUCH_PROMPT`

payloadから投稿情報を受け取り、ビルダーへ渡す:


### 変更3 — `chrome-extension/background/service_worker.js` の `handleS1TouchStart()`

`GET_TOUCH_PROMPT` 呼び出しに投稿情報を追加:

```js
bridgeResp = await callWebAppBridge(webappTabId, 'GET_TOUCH_PROMPT', { handle, tweetText, tweetUrl })
```

### 変更4 — `src/components/tabs/Tab2.tsx`（CaseCard）

`handleCopyPrompt()` と `handleCopyAndOpenGemini()` の `buildTouchPrompt(item, touches)` 呼び出し（inbound/dm以外の分岐）に targetPost を渡す:

```ts
const targetPost = (tPostUrl.trim() || tPostRawText.trim() || tPostText.trim())
  ? { url: tPostUrl, text: tPostRawText.trim() || tPostText.trim(), postedAt: tPostDateTime }
  : undefined
prompt = await buildTouchPrompt(item, touches, targetPost)
```

（OS②選択の自動入力で `tPostUrl` / `tPostText` が埋まっているケースが主対象。フォームが空なら従来どおり targetPost なし）

### 変更5 — 案内文言の更新（スクショを「必須」から「任意」へ）

- `gemini_filler.js` の S1取込パネル手順: 「② スクショを追加して送信」→「② そのまま送信（画像・リプ欄が重要な時だけスクショ追加）」
- 同様にOS②タッチ取込パネル（`showTouchCapturePanel`）の手順も更新
- `s1_touch_scanner.js` の成功トースト: 「スクショ追加後、送信して【取込】を押してください。」→「Geminiでそのまま送信してください（スクショ追加は任意）。」
- ただし**投稿本文が取得できなかった場合**（`tweetText` が空）はプロンプトにセクションが付かないため、従来文言のままにする（S1パネル表示時に `ctx.tweetText` の有無で文言を切り替える。`s1_touch_context` に `tweetText` は既に入っている）

## 受け入れ基準

1. x.comを新規タブで開いて最初に表示されたプロフィールのツイートに「OS②選択」ボタンが（3秒以内に）表示される
2. タイムラインを高速スクロールして戻っても、ボタンが消えたツイートが自動復活する（3秒間隔のセーフティネット）
3. Gemini等の別タブから戻った直後にボタンが揃っている
4. S1接触を押す → Geminiに挿入されたプロンプトの末尾に【今回の接触対象投稿】セクションがあり、投稿URL・本文が入っている
5. その状態で**スクショを添付せずに送信**しても、AIが投稿本文を対象としてTOUCH出力を返し、取込→A/Bパネルまで完走する
6. Tab2でOS②選択経由のタッチ追加フォーム（URL・本文入り）から「コピーしてGeminiを開く」→ プロンプト末尾に同セクションが入っている
7. 投稿本文が取得できないケース（引用RTや画像のみ投稿等）では従来どおりスクショ添付の案内が出る
8. `npm run build` 成功
